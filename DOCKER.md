# Docker

Как собрать и запустить GasVision Трекер в Docker для локального использования
командой или для деплоя на сервер.

## Что внутри

- **Один контейнер** (`app`) — сам Next.js-сервер (`next start`).
- **SQLite** как база данных — файл `dev.db` лежит в именованном Docker-томе
  `gasvision_data`, поэтому переживает пересборки и перезапуски контейнера.
- При каждом старте контейнера **entrypoint** сам накатывает миграции
  (`prisma migrate deploy`) и досеивает системные колонки, если их ещё нет
  (`prisma db seed`) — это безопасно запускать повторно.
- Образ **не** использует Next.js `output: "standalone"`: в контейнере
  остаётся полный `node_modules`, потому что на старте нужен Prisma CLI и
  `tsx` для сидинга, а Prisma использует нативный драйвер `better-sqlite3`.
  Компромисс — образ немного тяжелее, зато не приходится гадать, что именно
  standalone-трейсинг Next.js забыл упаковать из нативных бинарников.

## Требования

- Docker Engine 24+ и Docker Compose v2 (команда `docker compose`, не
  `docker-compose`).

## Быстрый старт

```bash
cp .env.docker.example .env
# впишите в .env свой AUTH_SECRET (см. ниже)
docker compose up -d --build
```

Открыть [http://localhost:3000](http://localhost:3000).

Логи:

```bash
docker compose logs -f app
# или: npm run docker:logs
```

Остановить:

```bash
docker compose down
```

Данные (файл SQLite) при этом **не удаляются** — они лежат в томе
`gasvision_data`, а не в контейнере.

## Переменные окружения

`docker compose` сам подхватывает файл `.env` рядом с `docker-compose.yml`
(не путать с `.env` для локальной разработки — они разные, `.env` для
Docker в `.gitignore`, коммитим только `.env.docker.example`).

| Переменная | Обязательна | Назначение |
| --- | --- | --- |
| `AUTH_SECRET` | да | Ключ для подписи сессий Auth.js. Сгенерировать: `openssl rand -base64 32`. Контейнер откажется стартовать без него. |
| `AUTH_TRUST_HOST` | нет (по умолчанию `true`) | Auth.js в production-режиме по умолчанию отклоняет запросы с "недоверенным" host-заголовком (`UntrustedHost`). Нужно `true`, если приложение открывается напрямую по IP/домену или стоит за reverse-proxy. Не трогайте, если не уверены. |
| `APP_PORT` | нет (по умолчанию `3000`) | На каком порту хоста публиковать приложение. Сам контейнер всегда слушает `3000` внутри сети Docker. |

`DATABASE_URL` **не** задаётся вручную — `docker-compose.yml` жёстко
прописывает `file:/data/dev.db`, что указывает на смонтированный том.
Менять это без необходимости не нужно.

## Хранение данных

SQLite-файл живёт в именованном томе `gasvision_data`, смонтированном в
`/data` внутри контейнера.

Посмотреть тома:

```bash
docker volume ls | grep gasvision
```

**Бэкап** базы (контейнер может быть запущен):

```bash
docker compose cp app:/data/dev.db ./dev.db.backup
```

**Восстановление** из бэкапа:

```bash
docker compose down
docker compose cp ./dev.db.backup app:/data/dev.db
docker compose up -d
```

**Полный сброс** (удалить все данные и начать с чистой БД):

```bash
docker compose down -v
docker compose up -d --build
```

## Миграции схемы БД

Порядок работы такой же, как без Docker — **миграции создаются локально**,
контейнер их только применяет:

1. Меняете `prisma/schema.prisma` у себя на машине.
2. Локально: `npx prisma migrate dev --name <название>` — это создаёт файл
   миграции в `prisma/migrations/` и применяет её к вашей локальной
   `dev.db`.
3. Коммитите новую папку миграции вместе с изменением схемы.
4. На сервере: `git pull`, затем `docker compose up -d --build` —
   entrypoint при старте выполнит `prisma migrate deploy` и применит новые
   миграции к БД в томе.

Внутри уже запущенного контейнера миграции вручную не гоняем — просто
пересобираем и перезапускаем сервис.

## Пересборка после изменений в коде

```bash
docker compose up -d --build
# или: npm run docker:up
```

Docker сам закэширует слой `npm ci`, если `package.json`/`package-lock.json`
не менялись — пересборка кода обычно быстрая.

## Продакшен / сервер за reverse-proxy

Если ставите Nginx/Caddy/Traefik перед контейнером (для HTTPS и домена):

- проксируйте на `127.0.0.1:${APP_PORT}` (или `app:3000` внутри той же
  docker-сети);
- прокидывайте заголовки `Host`, `X-Forwarded-For`, `X-Forwarded-Proto`;
- `AUTH_TRUST_HOST=true` обязателен — без него Auth.js будет отклонять
  запросы с чужим для него host-заголовком (ошибка `UntrustedHost`).

## Диагностика

**Контейнер падает сразу после старта с сообщением про `AUTH_SECRET`**
Не создан `.env` или в нём пусто значение `AUTH_SECRET` — см. «Быстрый
старт».

**`UntrustedHost` в логах**
`AUTH_TRUST_HOST` не установлен в `true` — проверьте `.env`.

**Ошибка компиляции `better-sqlite3` при сборке образа**
Значит в стадии `deps` не хватает системных пакетов для сборки нативных
модулей. В `Dockerfile` для этого уже стоят `python3 make g++` — если
ошибка всё равно возникает, скорее всего сборка идёт под архитектуру,
для которой у `better-sqlite3` нет прекомпилированного бинарника (см. флаг
`--platform` у `docker build`, если собираете на Apple Silicon для x86_64
сервера, или наоборот).

**Порт 3000 уже занят**
Смените `APP_PORT` в `.env` и перезапустите `docker compose up -d`.

## Локальная разработка — без изменений

Docker нужен только для сборки готового образа/деплоя. Для разработки
по-прежнему используем `npm run dev` и локальный `dev.db` — так быстрее
из-за hot reload, и не нужно пересобирать образ на каждое изменение.
